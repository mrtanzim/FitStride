# FORGE — Project Analysis Report

Generated by Kiro analysis step.

---

## Summary

FORGE is an **AI gym mentor Flutter app** (Android-first) targeting intermediate gym-goers in Bangladesh. The project is well-documented and architecturally sound, with a complete design system and one polished screen (Home) implemented. The codebase is currently at **end of Phase 1** — the design shell is done but all backend, data, and feature work has not yet started. The project is in excellent shape to proceed; there are no critical bugs, but several gaps must be filled before the app is usable.

## 4. State Management Approach

**Riverpod** is the chosen approach (from Architecture.md and Rules.md), and `ProviderScope` is correctly placed at the root in `main.dart`.

**However**, the only currently implemented screen (`HomeScreen`) uses `setState` exclusively for local UI state (`_waterLiters`, `_eggsCount`). This is appropriate for local ephemeral state, but it is noteworthy that:

- No `Provider`, `StateProvider`, `NotifierProvider`, or `AsyncNotifierProvider` has been defined yet.
- No repository layer exists yet.
- No providers file in any feature folder.

This is acceptable at Phase 1 — Riverpod providers will be introduced when real data wiring begins in Phase 2+. The foundation (ProviderScope wrapping the app) is correct.

## 5. Navigation Pattern

**go_router `StatefulShellRoute.indexedStack`** — implemented correctly:

- 4 tabs: Home `/`, Plan `/plan`, Mentor `/mentor`, Progress `/progress`.
- Note: the router has 4 branches but the nav bar shows 4 tab items with a center "+" button — the 5-slot layout from Design.md (Home, Plan, **Log**, Mentor, Progress). The "Log" center button is **not a route** — it triggers `_showQuickLogSheet(context)` directly. This is the correct approach per the design.
- The `onTalkToMentor` callback in `HomeScreen` is wired but has an empty body (`// Switch to mentor tab`). This needs to be connected: `navigationShell.goBranch(2)`.
- Deep linking is supported by go_router but not yet configured.
- Route guards (auth check → onboarding → home) are planned for Phase 2.3 but not yet implemented.

## 7. Notable Patterns, Issues, and Areas for Improvement

### Strengths

1. **Excellent documentation.** PRD, Architecture, Design, Rules, Phases, Memory — all 6 documents are current, detailed, and consistent. This is the project's biggest asset.
2. **Solid design system.** All color, typography, spacing, and radius tokens are defined and used correctly — no magic numbers in widget files.
3. **Custom painter muscle silhouette.** `MuscleSilhouette` uses a full anatomical `CustomPainter` with glowing lime highlights for target muscles. This is unique and design-accurate.
4. **`GlassCard` uses `BackdropFilter`** — correct approach for the glass morphism effect.
5. **Press animation in `LimeButton`** — `AnimatedScale` at 0.98 on tap down is subtle and correct per Design.md.
6. **`MentorOrb` animation** — looped `AnimationController` with proper `dispose()` — no memory leak.
7. **Config via `--dart-define`** — no secrets in code. `AppConfig.supabaseUrl` defaults to empty string.

### Issues / Gaps

1. **`core/strings.dart` is missing.** Rules.md explicitly requires all user-facing strings to go through `core/strings.dart`. Currently, strings like `'Good Morning, Tanzim'`, `'Chest + Triceps'`, `'No Sugar Challenge'` are hardcoded directly in `home_screen.dart`. This is fine for placeholder UI but must be fixed before the real data layer is wired in.

2. **Hardcoded user data everywhere in HomeScreen.** `home_screen.dart` contains `'Good Morning, Tanzim'`, `'12 days'`, `'Strict Coach'`, `'Chest + Triceps'`, `'6 exercises • 55 min'`, `'3 of 5 done'`, `'Day 9 of 30'` etc. These are correct placeholders for the visual gallery phase, but the entire screen needs to be rebuilt with real providers before Phase 6 is complete.

3. **`onTalkToMentor` callback is a no-op.** In `router.dart`, `HomeScreen(onTalkToMentor: () { /* Switch to mentor tab */ })` does nothing. Should be `() => navigationShell.goBranch(2)`.

4. **Phase 1.5 (Design Gallery) not done.** `Phases.md` still has this unchecked. Low priority but should be ticked off or explicitly dropped.

5. **`core/errors/`, `core/services/`, `core/utils/` directories are empty.** These need `supabase_client.dart`, `notification_service.dart`, `local_db.dart`, `app_exception.dart`, `error_handler.dart` as planned in Architecture.md. They will be populated in Phase 2.

6. **No route guards.** Any user who opens the app goes straight to Home. Auth + onboarding redirect logic (Phase 2.3) is not implemented yet. This is expected.

7. **`AppColors.bgDeep` minor token mismatch.** `Design.md` defines `bgDeep = Color(0xFF050A07)` but `colors.dart` has `bgDeep = Color(0xFF060907)`. One byte off. Not visually significant but worth aligning.

8. **Quick Log sheet items are non-functional.** The 6 tiles (Water, Protein, Meal, Weight, Workout, Slip) in `router.dart` are display-only — tapping them does nothing. Expected at this phase.

9. **`home_screen.dart` is 440+ lines.** Rules.md says max ~300 lines per file. The screen should be split when real data is wired: pull the 5 section builders into separate widget files under `features/home/presentation/widgets/`.

10. **No `SectionHeader` shared widget.** Architecture.md lists `SectionHeader` as a core widget, but it hasn't been created yet. Currently section labels are built inline.

11. **No `ProgressRing` shared widget.** Listed in both Architecture.md and Design.md as a core component, not yet created.

12. **Test coverage is minimal.** One smoke test confirms 5 strings render. No unit tests exist for any business logic. Rules.md requires unit tests for streak calculation, slip reset, daily totals, personality lock check, and plan JSON validation — all to be added as those features are built.

13. **`AppText.button` size mismatch.** `Design.md` specifies button text at `16 / 600` but `typography.dart` defines it as `fontSize: 14, fontWeight: w700`. Minor inconsistency.

14. **`StatefulShellRoute` has only 4 branches but 5 nav slots.** This is intentional and correct — the center "+" is not a navigation branch. Worth a comment in `router.dart` for clarity.

## 8. Recommendations (Ordered by Priority)

### Immediate (before Phase 2)

1. **Fix the `onTalkToMentor` no-op.** One line: `onTalkToMentor: () => navigationShell.goBranch(2)`. Takes 30 seconds.

2. **Create `core/strings.dart`** with at least the placeholder strings from `home_screen.dart`. This unblocks Rules.md compliance and makes string updates trivial later.

3. **Align `bgDeep` token.** Change `colors.dart` line from `0xFF060907` to `0xFF050A07` to match `Design.md`.

4. **Add a comment** in `router.dart` explaining that the 4-branch shell intentionally has no branch for the "Log" center button, which is a modal sheet, not a tab.

### Phase 2 prerequisites

5. **Add `supabase_flutter` to `pubspec.yaml`** and initialize in `main.dart` before `runApp`. Pull URL and anon key from `AppConfig`.

6. **Create `core/services/supabase_client.dart`** as a thin singleton wrapper around `Supabase.instance.client`.

7. **Implement auth route guards** in `router.dart` using go_router's `redirect` callback: unauthenticated → `/auth`, authenticated but not onboarded → `/onboarding`, else Home.

### Phase 3+ (as features are built)

8. **Split `home_screen.dart`** into `widgets/mentor_card.dart`, `widgets/workout_card.dart`, `widgets/missions_card.dart`, `widgets/challenge_card.dart`. The screen file becomes a shell under 100 lines.

9. **Create `SectionHeader` and `ProgressRing` shared widgets** — both are referenced in Architecture.md and will be needed in multiple screens.

10. **Introduce Riverpod providers** for each feature as it is built: `AsyncNotifierProvider` for remote data, `NotifierProvider` for local UI state that needs to survive widget rebuilds.

11. **Write unit tests alongside each domain layer addition** — streak logic, daily totals grouped by local date, plan JSON schema validation, personality lock date math.

### Before release

12. **Audit `home_screen.dart` hardcoded strings** when real data is connected — none of the placeholder strings should remain by Phase 6.

13. **Verify `textSecondary` contrast** on the glow area meets 4.5:1 — `#9AA39C` on `#0D2A18` is approximately 3.8:1 and may fail WCAG AA. Consider lightening to `#A8B2AB`.

## 9. Conclusions

The FORGE project has an **exceptionally strong foundation** for a solo vibe-coding project. The documentation is better than most production codebases, the design system is complete and consistently applied, and the approved Home screen is a high-fidelity implementation of the design reference. The architecture decisions (Riverpod, go_router, Supabase Edge Functions for LLM, offline-first workout logging, server-side personality lock) are all sound.

The project is at a natural inflection point: the visual shell is done and the backend work is about to begin. The next critical path is **Phase 2 (Auth + DB)** → **Phase 3 (Onboarding)** → **Phase 4 (Plan + Edge Function)**. These three phases together will produce the first end-to-end user flow.

The issues identified are all **expected at this stage** — no architectural mistakes need to be undone. The handful of minor inconsistencies (string centralization, token value, file length) are low-effort to fix and should be addressed before heavy feature work begins to keep the codebase clean.
